A1

One-line installer (macOS / Linux)

Working
What it does
Installs the fox binary with one command.
How it works
deploy/install.sh detects OS (darwin/linux) and arch (arm64/amd64), downloads fox-<os>-<arch> from the GitHub release, verifies it against the release's SHA256SUMS (verify_file, using sha256sum or shasum), installs to $PREFIX/bin (sudo only if needed). On macOS it also stages fox-linux-<arch> into $PREFIX/share/foxbyte for the VM.
How to use
curl -fsSL https://raw.githubusercontent.com/thefoxbyte/foxbyte/main/deploy/install.sh | sh · env FOX_VERSION, FOX_REPO, FOX_DIST (local folder), FOX_PREFIX (default /usr/local).
How to test
Unit: scripts/test_install_sh.sh (run by CI) against a fake release — a verified release installs; a tampered binary, a release without SHA256SUMS and an asset missing from the listing each install nothing; FOX_NO_VERIFY=1 installs anyway; a local FOX_DIST build still installs. Manual: FOX_DIST=./dist FOX_PREFIX=$HOME/.local sh deploy/install.sh then fox version.
Status & limits
Working. Every download is checked against the release's SHA256SUMS before it is installed, and anything that cannot be verified stops the install (FOX_NO_VERIFY=1 skips deliberately; FOX_DIST is the user's own build, so there is nothing to check it against). The listing travels over the same TLS connection as the files, so this proves integrity — a complete, unaltered download — not authorship; signatures are still not built. Signed (22 Sep 2026, audit v2 G22): it also checks SHA256SUMS.sig, an Ed25519 signature by the FoxByte release key, against the public key in the script itself (which comes from the repository, not the release) with openssl pkeyutl -verify -rawin. A release without a signature, or signed by another key, is refused (FOX_ALLOW_UNSIGNED=1 installs an old, unsigned one on checksums alone). Where openssl cannot do Ed25519 — macOS ships LibreSSL — it says the signature was not checked and carries on, unless FOX_REQUIRE_SIGNATURE=1; fox checks it on every update. Tested with OpenSSL 3 and with macOS's LibreSSL (scripts/test_install_sh.sh).

c9afda7 (PR #1); URLs repointed to the foxbyte org in 0b125f9.

A8

New-release notice on fox start

Working
What it does
When a newer release is published, fox start ends with one line: FoxByte vX is available (you have Y). Run `fox update` to get the new capabilities. No prompt, and start is never held up.
How it works
New package internal/update. The check starts in the background when start begins and gets 1.5 s; the notice prints after start's own output only if the check finished in time. It lists releases through the GitHub API (not /releases/latest, which can point at a release still being published) and offers only one that is newer, not a draft or prerelease, and has every file this platform's update needs attached. That is a single request: it does not download SHA256SUMS, because GitHub throttles repeated downloads of the same release asset (measured 16 Sep 2026 from this Mac: 0.5 s the first time, then 7 s–75 s), so the first check after a new release was fast and every later one missed the budget. fox update still downloads SHA256SUMS and verifies every file before installing anything. The releases list is cached with its ETag in ~/.fox/update-check.json, and a newer release, once found, is remembered in ~/.fox/update-notice.json for 6 hours, so the notice keeps printing without a request. "Up to date" is never remembered, so every other start asks — a conditional request that GitHub answers with a 304 when nothing changed, which does not count against its rate limit. Runs on the computer: in host.Maybe around the forwarded start on macOS/Windows, and in start itself on Linux; the engine inside the VM never checks. Offline, rate limited or any error: nothing printed.
How to use
Automatic. FOX_NO_UPDATE_CHECK=1 turns it off; FOX_UPDATE_CHECK_TIMEOUT (e.g. 3s); FOX_UPDATE_CHECK_INTERVAL sets how long a found release is remembered (default 6h; 0 checks on every start); FOX_REPO like the installers. Development builds (0.1.0-dev) never check.
How to test

What it does

How it works

(5) With the new engine: fox up (running containers left alone; main's Blackbox re-applied), fox ledger upgrade --all, fox start. (6) Replaces fox on the computer — macOS: write-and-rename (sudo if needed); Windows: the running bb.exe is renamed to bb.exe.old and the new one copied in — keeping the previous copy in ~/.fox/updates/prev/, and refreshes the engine fox setup would install. How it works

PostgreSQL major upgrade

Working
What it does
Moves an install from the PostgreSQL major its data was created with to the one this fox ships, keeping every database, role, API key and Blackbox entry — after showing every change, asking, and taking an export. The old databases are kept until the user deletes them, so it can be undone.
How it works
internal/branch/pgupgrade.go, orchestrated by host.RunUpgrade (plan → confirm → export → apply, one code path for macOS, Windows, Linux and inside the VM). Plan: each branch's major from PG_VERSION, which are carried (not agents'), HA state, the storage, and the PostgreSQL changes crossed — pgNotes, written by hand from each release's Migration section, each with a probe run on every running branch, so changes found in the user's own data are listed first (an expression index, an MD5 password, an inheritance tree…). Refusals: HA on, main served by the standby after a failover, main not running, a Blackbox that does not verify, branches on mixed majors, an earlier upgrade's databases still held. Apply: dump every carried branch with the new major's pg_dump (a suspended one is woken and its Blackbox verified first); remove the Postgres containers; move every branch dataset into a holding area outside the branch namespace (storage.stash: a sibling dataset under ZFS, a dot-directory under btrfs, so no listing or routing sees it); reload each carried branch into a new dataset on the new image, main first; check each Blackbox came across exactly; give the new main its own WAL archive prefix (a file in its dataset, outside PGDATA — a new cluster's segment names would otherwise collide with the old one's); take a base backup. H10

Checkpoints & anchors

Working
What it does
Takes tamper-evidence outside the database. At intervals it records a Merkle root over the newest ledger entries — in the database and as a read-only anchor file somewhere else — so rewritten, deleted or wiped history can be proven later.
How it works
bb.ledger_checkpoints (ledger_v2.sql) is append-only, and a trigger refuses any checkpoint that doesn't continue the last one (from_id = last to_id + 1, prev_root = last root). The engine (internal/branch/checkpoint.go) reads the new entries, refuses if their hash chain is already broken, and builds the anchor with internal/ledger/integrity.go: each leaf is sha256(0x00 ‖ recomputed row hash ‖ "|" ‖ capture hash), each node sha256(0x01 ‖ left ‖ right). It records the checkpoint, then writes ~/.fox/anchors/<branch>/<to_id>.json with mode 0444, never overwriting. A scheduler in the control plane checkpoints running branches every FOX_CHECKPOINT_INTERVAL (10m) or once FOX_CHECKPOINT_ENTRIES (500) are waiting; FOX_CHECKPOINTS=off disables it. FOX_ANCHOR_DIR moves anchors (e.g. to a write-once mount); FOX_ANCHOR_IMMUTABLE=1 adds chattr +i. The format is published in docs/ledger-anchor-format.md. Signed (22 Sep 2026, audit v2 G17): each anchor carries key_id and an Ed25519 signature over a fixed payload (ledger.SigningPayload, specified in docs/ledger-anchor-format.md), by ~/.fox/anchor-signing.key or FOX_ANCHOR_KEY — a file no database can read. fox blackbox anchor-key prints the public key. Off the machine (22 Sep 2026): with a remote backup target, every anchor — each branch's and the security log's — is copied to <target>/anchors/<dir>/ after it is written (MirrorAnchors; a .mirrored marker beside each, so a failed copy is retried with the next checkpoint). In an Object Lock bucket it cannot then be changed or deleted before its retention ends, even by whoever controls this machine.
How to use
fox ledger checkpoint [branch] · POST /api/branches/{name}/ledger/checkpoint · web Integrity page → Create checkpoint
How to test
Unit: internal/ledger/integrity_test.go. integration-v2 §3: anchor written read-only in the published format; no-op when nothing is new; the database refuses an out-of-sequence checkpoint; checkpoints are append-only. §3b: the scheduler anchors new entries on its own.
Status & limits
Verified in the VM (integration-v2 §3 and §3b, 14 Sep 2026). Anchors are only as trustworthy as where they're stored — the default directory is on the same host, so point FOX_ANCHOR_DIR at storage the database's operators can't rewrite. Entries written since the last checkpoint are protected by the hash chain only. Cloud write-once anchor writers (S3 Object Lock etc.) are not built (commercial scope). A cloned branch inherits its parent's checkpoint rows but not its anchor files. A signature proves an anchor came from the key holder; on one machine the administrator is one, so anchors held elsewhere remain the proof against them. Off-host storage (S3 Object Lock) comes with the remote backup target.

H15

Policy gate (warn / block)

Working
What it does
Checks every schema change against policy rules before it runs. A warn rule lets the change through and tells the client why it is risky; a block rule refuses it. Tools and agents get a machine-readable answer they can act on, defined in the published contract docs/policy-errors.md.
How it works
internal/ledger/policy.sql, installed after the 2.0 objects by EnsureLedgerV2 (every fox start, fox blackbox upgrade). Rules live in bb.policy_rules (rule id, command tag, optional case-insensitive regex over the statement, warn|block, reason, hint, enabled); changes go to the append-only bb.policy_rule_history with who made them. The event trigger bb_policy_start fires on ddl_command_start after the guardrail bb_guard_start (name order). Warn: an evaluation row and a NOTICE with SQLSTATE BBX02. Block: a BLOCKED Blackbox entry (risk policy) and an evaluation written through dblink so they survive the rollback, then an ERROR with BBX01; blocks win over warnings. DETAIL is one-line JSON (v, rule_id, action, command, matched, reason, hint, override, evaluation_id, blackbox_id, impact). Override: superusers and db_admin members may SET bb.policy_allow = '<rule ids>'; it is recorded as an allowed evaluation and in the capture row's override_used; bb.allow_destructive does not override policy. Fail-safe: any error while matching or recording becomes a WARNING and never stops a statement a warn rule matched; a block still refuses (with evaluation_id null). The gate ignores the client-settable bb.v2; a superuser turns it off with ALTER EVENT TRIGGER bb_policy_start DISABLE. Rule changes through REST need db_admin on that branch (IsAdmin); clients can read rules and evaluations but not write them. The existing guardrail (bb.policy, DROP TABLE/SCHEMA, SQLSTATE 42501) is unchanged.
How to use

H17

Impact analysis

Working
What it does
Before a schema change runs, shows what it would affect: what depends on the object, which other branches have it, what the policy gate would say, and how risky it is overall — for people (fox impact) and for agents (MCP impact, and inside every execute_change result).
How it works
Target: ledger.ParseTarget reads the statement to find the table, view, materialized view, index or sequence it changes and, where relevant, the column and kind of change (drop, drop-column, alter-column-type, rename, rename-column, truncate are destructive; alter, alter-column, create-index, grant, revoke are not). Quoted and schema-qualified names work; --object/--column name it directly. Dependents: the read-only SQL function bb.blast_radius(target, column, depth) (internal/ledger/impact.sql, installed by EnsureLedgerV2, runs with the caller's rights and search path, so an unqualified name resolves as in the caller's own statement) walks pg_depend for normal and automatic dependencies and reports each dependent's type, identity, owning relation, depth and the view it was reached through: views and materialized views (and views on those, up to depth 5, capped at 10), constraints including foreign keys from other tables, indexes, triggers, row-level security policies, defaults, owned sequences and SQL-standard functions. For a column, only what uses that column. Every reported name is schema-qualified, and an index is reported against the table it indexes. Branches: every other running branch is checked for the object (and column) without waking suspended ones, with the branch it was cloned from (ZFS origin, btrfs parent UUID). Policy: the rules the statement would trigger (H15). Score (scoreImpact): destructive 5, otherwise 1; each dependent view, function or foreign key from another table +3, trigger or policy +2, index or other +1; deeper than checked +3; ≥10k rows +1, ≥1M +3; each other running branch with it +1 (max 5); a blocking rule +5, a warning +2. 15+ high, 5–14 medium, below low; every point is listed as a reason.
How to use
fox impact "ALTER TABLE orders DROP COLUMN note" · fox impact --object orders_summary --json · fox impact "DROP TABLE orders" --branch qa · REST POST /api/branches/{n}/impact with {"sql": …} or {"object": …, "column": …} · MCP impact · SQL: SELECT bb.blast_radius('public.orders', 'note')
How to test
Unit: internal/ledger/impact_test.go (TestSchemaImpact — read-only, capped depth, caller's rights; TestParseTarget — 27 statements; TestTargetDestructive) and internal/branch/impact_test.go (TestScoreImpact, TestBranchParentParsing — ZFS and btrfs output, TestFormatImpact). integration-v2 §8: a table's views (depth 1 and 2, via), the foreign key from another table and its index; a column's dependents only; quoted names; non-destructive changes; a missing object; a statement without a target asks for --object; a view's dependents; the depth limit; the object on a branch cloned after it existed (with its parent) and not on one without it; the policy verdict in the score; REST and MCP agree with the CLI; execute_change includes the impact.
Status & limits
Verified in the VM (integration-v2 §8, 15 Sep 2026; existing suite 28 / 28). The target is read from the statement text: one object per statement (the first of a multi-object DROP), and statements on functions, types, schemas or whole-schema grants aren't recognised — name the object with --object. Dependencies PostgreSQL doesn't record aren't seen: application queries, functions with plain-string bodies (only SQL-standard BEGIN ATOMIC bodies are tracked), dynamic SQL, other databases. Row counts are the planner's estimate. The score is a guide, not a guarantee. The policy error DETAIL's impact field stays null (the gate doesn't run this inside the database); use fox impact or execute_change. No web view yet.

H18

Blackbox diff between branches

Working
What it does
Shows which schema changes distinguish two branches: where they split, what was changed only on each since, and which objects were changed on both (likely conflicts). Diff only — nothing is merged or changed.
How it works
branch.DiffLedgers (internal/branch/diff.go) reads both branches' Blackbox histories in id order (starting a suspended branch first, as other Blackbox commands do). A branch is a copy-on-write clone, so it begins with its parent's history entry for entry; the fork point is the longest run of entries with the same id and the same recomputed hash. Everything after it is listed for each side (id, time, command, object, status, actor). Objects changed on both sides are listed with their entry ids; BLOCKED entries don't count, since those changes never happened. Each branch's parent is read from the storage layer.
How to use
fox blackbox diff main qa · fox branch diff main qa --json · REST GET /api/blackbox/diff?a=main&b=qa (also /api/ledger/diff) · MCP blackbox_diff
How to test
Unit: internal/branch/impact_test.go TestBuildDiff (fork point, same id with different content, both-changed objects, BLOCKED ignored, self diff, no shared history, text output). integration-v2 §8: a branch cloned from main, changes on each side — the parent, shared history, changes only on main, only on the branch, the object both changed; fox branch diff matches; text output; a branch against itself; REST on both paths; unknown branch 404; MCP.
Status & limits
Verified in the VM (integration-v2 §8, 15 Sep 2026; existing suite 28 / 28). It compares recorded schema changes, not the schemas themselves: changes made while Blackbox wasn't recording (before it was installed, or with the capture turned off by a superuser) don't appear, and data changes are out of scope. Branches that weren't cloned from each other (e.g. two imports) have no shared history, so everything shows on both sides. Rewritten history on one branch moves the fork point earlier — check fox blackbox integrity. Reads both histories in full.

How it works
