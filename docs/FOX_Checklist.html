Storage engine — not implemented, by design

FoxByte does not have its own storage engine. Data is stored by PostgreSQL's own engine (heap tables, B-tree indexes, write-ahead log) running on local disk inside the stock postgres:18-bookworm image plus wal-g (postgres:16-bookworm for an install created before 21 Sep 2026). This was a locked architecture decision: a Neon-style engine that separates compute from storage over the network adds latency to every transaction, and transaction speed must never be compromised.

What is built is a storage layer around Postgres: copy-on-write branch drivers — ZFS on macOS/Linux, btrfs on Windows — behind one interface in internal/branch/storage.go (C1), quotas (C6), capacity reporting (C7), and durability to object storage with wal-g + MinIO: WAL archiving, base backups, point-in-time restore (D1–D3). Networked storage disaggregation is listed in the README roadmap but not started (see "Not started").

Suggested next steps

  1. The claims are checkable now: a restore is proved weekly and by fox backup verify (D2), a tag cannot ship past a red or stale nightly (M2), every command the engine runs has a deadline so nothing hangs for ever (G30's useful half), containers restart on crash (B2), and CI runs the race detector. Before this, the most consequential thing the product claims — that the backups restore — had never been tested end to end on a real install.
  2. This checklist's own badge rule is enforced (audit v2 G31): no row can be badged done while carrying an open sub-item, and scripts/test_feature_checklist.sh fails the build if one is. The 45 sub-items that broke the rule were each put somewhere honest — built, a limit (!), planned (→), or a note in "Tested by" — and nine of them turned out to be things we had already shipped and never ticked off, including automated UI tests, per-user access control, SDK contract tests and the first signed release.
  3. Run on real machines what the throwaway VM cannot: fox update across a real release on macOS and Windows (A9); on Windows, the zstd distro image's unpack (M5), the btrfs holding area of fox pg upgrade (D6), and an export's copy to the host (D5).
  4. Automated tests for the imports (I1–I3, I7) — the last area with none.
  5. Gate release tags on the nightly suites, so a tag cannot ship past a red suite (M2).
  6. Decide how this checklist shows partial work (audit v2 G31): 9 features are badged done while carrying an open sub-item (C7, D5, D6, F5, G3, H16, H17, I13, M7) — down from 34. Each of those sub-items is a disclosed limit rather than unfinished work, so the remaining question is whether a limit belongs in the sub-item list at all.
  7. The object store's images are FoxByte's own (M6): MinIO left Docker Hub in 2026 and then quay.io stopped serving it anonymously — every tag there answers 401 — so a fresh install on macOS or Linux could not start, while existing installs carried on from their cache and Windows carried on because its distro image ships them inside it. They are mirrored to ghcr.io/thefoxbyte by .github/workflows/mirror-images.yml, which takes them out of a published release's distro asset rather than from a registry that will not serve us. Run it once and pin what it prints. It can only be dispatched after it is on the default branch, and until the digests are pinned release.yml refuses to publish.
  8. Promotion is built (H18, audit G29): a branch's recorded statements, reviewed, then applied to another branch in one transaction — attributed to whoever wrote them, with the approver beside them. Schema only. An agent can propose and cannot approve its own request.
  9. From the audit, deliberately left: HA beyond the demo — automatic failover and fencing across hosts (D4, G21); metrics and alerts, and supervision of the background servers themselves (B2, G27 — the containers restart); splitting the branch package and running its SQL through pgx (G30 — the deadlines are in); quotas on btrfs and per-branch CPU/memory (C6, G33).

D4HA standby & failover
  • Streaming hot standby
  • Manual failover, main rerouted
  • Nothing deletes or stops the promoted standby
  • fox up brings it back, not the old main
  • fox ha failback, keeping every write
  • The promoted standby archives WAL, so backups and PITR cover the failover
  • With the change feed on, the standby’s own physical slot and a conninfo with a database name, so realtime subscribers keep their position across a promotion (N1)
  • A replication role of its own (HA plan phase 1, first item): db_replica copies the database and can read none of it, admitted by one pg_hba rule naming it and this install’s own network. Replaces host replication all all plus a standby connecting as the bootstrap superuser — the wide rule is deleted rather than outranked, the superuser can no longer replicate over the network while its ordinary connections are untouched, and fox check warns on an install whose HA was enabled by an older version and still carries the old rule
  • TLS on replication, and publishing a primary at all (HA plan phase 1): fox node expose — opt-in, one address, TLS required with a per-install CA the standby verifies, db_replica only, one peer /32 only. Verified between two machines: without TLS refused, the superuser refused even over TLS, a real base backup over TLS succeeded. The private key is kept out of PGDATA, which pg_basebackup copies. The join token carries the CA and one role’s password — never the install secret, from which the superuser’s could be derived
  • A standby node is told what its licence costs it (HA plan §3.1): node join warns when this machine has no licence that unlocks the paid features — a licence is per-install state and joining copies the database, not ~/.fox, so a fresh standby has none and refuses paid features immediately on promotion, with no grace. Corrects the plan, which assumed a mismatched fingerprint lapses after 14 days: it never lapses, so the dangerous state is an absent licence, not a mismatched one
  • Reads from the standby (HA plan phase 7): a read-only session asks for the copy by name — main:standby, same key, same gateway — and the standby answers it instead of the primary, so a long report stops competing with the writes. On one machine that is process isolation rather than read scaling, and across two machines it is refused with the reason: a joined node’s copy carries the primary’s roles while that machine’s gateway has its own secret, which is plan §3.2’s shared state. The suffix is resolved before the ACL, the key’s scope and the audit record, so it chooses a backend and never widens what a key may open; writes there are refused by Postgres itself; and the name is refused — naming the command that fixes it — when there is no standby, when the branch is not main, when the standby is not running, and above all when the standby has been promoted, where quietly serving the primary instead would undo the whole point. Staleness is reported rather than capped: ha status says how far behind the copy is and connect prints the endpoint with the caveat
  • Accounts and keys reach every node (HA plan phase 2): the primary writes users, api_keys, oauth_identities, branch_owners, pipelines, pipeline_targets and change_requests into statedb in the replicated cluster, and a machine that follows a primary elsewhere applies them into its own SQLite — so a failover no longer leaves nobody able to sign in. The store deliberately does not move into main: internal/auth never imports the engine, so signing in works while the database is down, which is the window the phase exists for. Exactly one node writes (a node ships only while it follows nobody, and a promotion clears that record), the document travels in the WAL already being streamed, a revoked key is deleted on the other node rather than merely not updated, statedb is closed to db_client and every role clients use, and an account change on a follower is refused instead of being silently overwritten. Sessions, the two append-only logs and the hash-chained security log are deliberately left behind, each for a stated reason
  • A promoted copy rewrites its role passwords (HA plan phase 2): a standby from another machine carries that install’s roles, whose passwords derive from its secret — which node join never carries — so a promotion used to leave every client unable to authenticate. The promoted node now rewrites the passwords of the roles this install manages, over the container socket that needs no password, leaving anything else alone; fox ha repair-roles is the hand crank. Clients are unaffected: they authenticate at the gateway with an API key. Measured: break one role’s password and the gateway refuses the connection; repair it and the same key works again
  • Automatic failover, refused without a witness (HA plan phase 3): fox ha watch on a standby promotes only when it and a witness on a third host both fail to reach the primary for --after. Two machines cannot tell a dead primary from an unreachable one, so the command refuses to run without a witness rather than working most of the time. Four decisions, one of which promotes; “the witness says the primary is fine” and “the witness could not be asked” are refused separately and logged differently. The promotion is the ordinary fenced failover — --force is not reachable from the watcher — and both promotions and refusals go into the hash-chained security log, which phase 2 keeps on each node. fox ha witness answers one question over HTTP and tells a stranger nothing: an unauthenticated ask gets 404, not 401. Not pg_auto_failover or Patroni: both want to own the data directory, the recovery configuration and the promotion, which this engine owns. What is left is two gateways behind a virtual IP, which waits on whether the customer supplies it
  • A drill that says what it actually tested (HA plan phase 6): a result carries the topology it ran in and who noticed, so the report stops disclaiming a second site it had or manual detection it did not use — with two machines and a watcher it says “Nothing it set out to” and names the one thing no drill can test, which is whether the witness is where the clients are. Detection is read from the security log, not passed as a flag, because the watcher is another process. fox ha drill --takeover measures a site failover from the surviving machine: it stops nothing and promotes nothing, RTO therefore includes noticing (the number a client experienced), and RPO is reported as not measurable from that side rather than as a zero that would read as a guarantee. A local drill is refused on a machine that follows a primary elsewhere, naming the one that applies
  • …and fox check’s licence line says it on every run, not just at join time — naming what a promotion would cost, or that a licence activated elsewhere survives one. The clause adds the consequence and never changes the severity
  • The licence policy for HA pairs is still a decision (plan §6.1) — site licence, fingerprint set, or per-node. Recommended: site licences, the only option needing no new code
  • Fencing across machines (HA plan phase 3, first half): ha failover on a machine following a remote primary refuses while that primary answers, because promoting would make a second one — a split brain that phase 1 shipped and that was measured (both machines accepting writes). Verified refused with the primary alive, promoted once it was stopped; --force warns before proceeding; a promotion says the old primary must re-join rather than restart as a primary. It cannot tell a dead primary from an unreachable one, which needs a failover manager
  • The rest of phase 3 — a failover manager for automatic detection — is a decision first: pg_auto_failover is installable for PG 18 but its last release predates it, and either manager wants to own synchronous_standby_names, which phase 5 made ours
  • A standby on another machine (HA plan phase 1, complete): fox node join <token> copies the primary over TLS and runs it as a standby, verifying that primary’s certificate. Demonstrated by killing the primary’s database with SIGKILL and promoting the survivor, which took writes with every acknowledged row intact. A promotion clears the join, since the survivor follows nobody; ha enable refuses on a joined machine rather than silently rebuilding the standby from the local main. Two VMs share a kernel and a disk, so this proves networking, credentials, TLS and promotion — not survival of a power cut
  • Failover drills (HA plan phase 6): fox ha drill --yes kills the primary with writes in flight, recovers through the real failover path, and writes a dated RPO/RTO report to ~/.fox/drills/. Measured 0 of 60 acknowledged writes lost and 400ms to service. The report refuses to let a figure be misquoted — zero under asynchronous replication is an observation, zero under zero-data-loss mode is a guarantee — and names what it did not test: losing a machine, noticing, and a second site
  • Zero data loss, opt in (HA plan phase 5): fox ha sync on|off — a commit waits until the standby has it on disk. Off by default; with one standby, if it stops writes stop, and the CLI says so. The release works while commits are stalled, a failover clears it so the promoted node is never left waiting for a standby it does not have, and fox check calls “on but nothing counted” a failure
  • Automatic failover, fencing, multi-host

    NRealtime change feed

    IDItem · scopeTested by
    N1Realtime change feed
    • Readiness as a verdict, not a refusal: realtime doctor classifies every table, realtime prepare makes the changes and prints them first
    • The cost ladder — primary key, then a unique index as the identity (same price, no schema change), then inserts-only, and REPLICA IDENTITY FULL last; --all never applies a costly fix
    • Only application tables stream: not bb, not Postgres’s, not an extension’s — and the application’s own schemas now do
    • Opt-in: fox realtime setup --yes says what it will restart; with the feed off, a primary's arguments are byte-identical to before and a branch gets none
    • Durable replay through ?since=<commit_lsn>, bounded by max_slot_wal_keep_size; past it the subscriber is told to resync rather than left waiting
    • One decoder per branch in the control plane, started on the first subscriber and stopped after the last; it wakes a suspended branch
    • A ?since= is judged before the stream opens (21 Oct 2026, found reviewing the realtime plan): it went to the decoder unchecked, and was silent both ways — a position the feed had read past attached the subscriber to the live stream with a hole in its copy and no event to say so, and a position ahead of the branch was reported to Postgres as flushed, so one request moved the slot past the end of the WAL and the branch's feed then delivered nothing to anybody, across restarts, with fox realtime slots still calling the slot idle. Four answers now: replay, join live, 400 when ahead of the branch's log, resync/cursor_expired when it cannot be replayed; a running fan-out keeps the floor it can honour, and the decoder checks the log end before acknowledging anything
    • An overflow inside one transaction says to refetch, not to resume: pgoutput proto 1 sends a transaction whole, so one larger than the buffer cannot be delivered at all, and the old advice replayed it for ever (measured: 31 of 100,000 changes, then 2) or skipped the rest of it silently. resync/tx_too_large names the size and the buffer; FOX_REALTIME_BUFFER raises it. The overflowed subscriber is also held attached until the decoder has acknowledged that transaction, so the feed moves past it instead of the next subscriber replaying it and overflowing in the same place. Falling behind across transactions is unchanged
    • Refusals that hold: row-level security (no override), no primary key (and UPDATE still works afterwards), anything outside public, the Blackbox's own tables, anything db_client cannot read
    • Wire format: values as text, identity always, old only when sent, changed only under FULL, unchanged-TOAST named rather than nulled

    • …and the limit is stated rather than implied: PostgreSQL copies a slot to the standby only while it is being consumed, so a continuously-read subscriber keeps its place through a promotion and one that read once and left is told to resync, as it was before
