Storage engine — not implemented, by design

FoxByte does not have its own storage engine. Data is stored by PostgreSQL's own engine (heap tables, B-tree indexes, write-ahead log) running on local disk inside the stock postgres:18-bookworm image plus wal-g (postgres:16-bookworm for an install created before 21 Sep 2026). This was a locked architecture decision: a Neon-style engine that separates compute from storage over the network adds latency to every transaction, and transaction speed must never be compromised.

What is built is a storage layer around Postgres: copy-on-write branch drivers — ZFS on macOS/Linux, btrfs on Windows — behind one interface in internal/branch/storage.go (C1), quotas (C6), capacity reporting (C7), and durability to object storage with wal-g + MinIO: WAL archiving, base backups, point-in-time restore (D1–D3). Networked storage disaggregation is listed in the README roadmap but not started (see "Not started").

Suggested next steps

  1. The claims are checkable now: a restore is proved weekly and by fox backup verify (D2), a tag cannot ship past a red or stale nightly (M2), every command the engine runs has a deadline so nothing hangs for ever (G30's useful half), containers restart on crash (B2), and CI runs the race detector. Before this, the most consequential thing the product claims — that the backups restore — had never been tested end to end on a real install.
  2. This checklist's own badge rule is enforced (audit v2 G31): no row can be badged done while carrying an open sub-item, and scripts/test_feature_checklist.sh fails the build if one is. The 45 sub-items that broke the rule were each put somewhere honest — built, a limit (!), planned (→), or a note in "Tested by" — and nine of them turned out to be things we had already shipped and never ticked off, including automated UI tests, per-user access control, SDK contract tests and the first signed release.
  3. Run on real machines what the throwaway VM cannot: fox update across a real release on macOS and Windows (A9); on Windows, the zstd distro image's unpack (M5), the btrfs holding area of fox pg upgrade (D6), and an export's copy to the host (D5).
  4. Automated tests for the imports (I1–I3, I7) — the last area with none.
  5. Gate release tags on the nightly suites, so a tag cannot ship past a red suite (M2).
  6. Decide how this checklist shows partial work (audit v2 G31): 9 features are badged done while carrying an open sub-item (C7, D5, D6, F5, G3, H16, H17, I13, M7) — down from 34. Each of those sub-items is a disclosed limit rather than unfinished work, so the remaining question is whether a limit belongs in the sub-item list at all.
  7. The object store's images are FoxByte's own (M6): MinIO left Docker Hub in 2026 and then quay.io stopped serving it anonymously — every tag there answers 401 — so a fresh install on macOS or Linux could not start, while existing installs carried on from their cache and Windows carried on because its distro image ships them inside it. They are mirrored to ghcr.io/thefoxbyte by .github/workflows/mirror-images.yml, which takes them out of a published release's distro asset rather than from a registry that will not serve us. Run it once and pin what it prints. It can only be dispatched after it is on the default branch, and until the digests are pinned release.yml refuses to publish.
  8. Promotion is built (H18, audit G29): a branch's recorded statements, reviewed, then applied to another branch in one transaction — attributed to whoever wrote them, with the approver beside them. Schema only. An agent can propose and cannot approve its own request.
  9. From the audit, deliberately left: HA beyond the demo — automatic failover and fencing across hosts (D4, G21); metrics and alerts, and supervision of the background servers themselves (B2, G27 — the containers restart); splitting the branch package and running its SQL through pgx (G30 — the deadlines are in); quotas on btrfs and per-branch CPU/memory (C6, G33).
